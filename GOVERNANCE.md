# AADM Standard — Governance Charter

> **The standard is the source of truth. Any MCP server, agent skill, IDE plugin, or hosted service that uses the name "AADM" enforces and echoes this repository — not the other way around.**

This charter exists because AADM is now implemented by multiple surfaces (hosted MCP, agent skills, IDE plugins, documentation portals). Without a written governance order, those implementations drift, and downstream users cannot tell whether they are reading the standard or one vendor's interpretation.

This file is **normative**. It applies to any tool, server, or document that claims AADM conformance.

---

## 1. Roles

| Role | Definition | Authority |
|------|------------|-----------|
| **Standard** | Markdown in this repository (`aadm-standard`). | Definitive source for AADM concepts, identifiers, vocabulary, obligations, and workflows. |
| **Implementation** | Any software that loads, surfaces, or enforces AADM content — including but not limited to the hosted MCP at `mcp.aadm.io`, agent skill bundles, CI linters, audit tooling. | Echoes and applies the standard. **MUST NOT** redefine identifiers, obligations, or workflow shape. |
| **Adopter** | An engineering organization using AADM in its own delivery process. | Free to extend the standard for its own needs (additional AUTH controls, internal seams, lane variants). Extensions are not "AADM" unless contributed back. |
| **Maintainer** | This repository's listed maintainers ([community/maintainers.md](community/maintainers.md)). | Merges, deprecates, and ratifies changes to the standard. |

## 2. Order of precedence

When sources disagree, this is the order in which the conflict is resolved:

1. **Statutory law and regulated control frameworks** that bind the adopter (HIPAA, GDPR, SOX, FedRAMP, etc.). The standard is never a substitute for legal counsel.
2. **The adopter's own written, ratified standards.** Local team standards win when they conflict with this document, *provided* the conflict is named explicitly in a written delta.
3. **This repository (`aadm-standard`)** — the markdown in `standards/`, `docs/`, `templates/`, this charter, and the conformance contract.
4. **Implementations** (MCP servers, agent skills, IDE plugins, etc.). When an implementation appears to contradict this repository, the implementation is in error and the standard is followed.
5. **Generated content** from AI agents, including content generated by tools that load AADM context. Agent output is a draft until verified against the standard and the adopter's tests.

## 3. What an "AADM implementation" must guarantee

Any tool that claims AADM conformance — including the hosted MCP — **MUST**:

1. **Preserve identifier semantics.** `AUTH-21`, `SEAM-04`, `TRACE-03`, `HANDOFF-04`, `AGENT-05`, `VERT_APP`, `HORI_SCHEMA`, `SIGL-08`, `L13` mean what this repository says they mean. Implementations may add catalog entries but must not silently re-number, re-letter, or repurpose existing ones.
2. **Preserve workflow shape.** Navigator has three stages (Scope → Verify → Readiness). Investigator has three stages (Investigate & evidence → Diagnose & classify → Scoped remediation). Sentinel has three stages (Scope & frame → Trace & bind evidence → Attest readiness). Each stage carries a human gate. An implementation that collapses these is non-conformant.
3. **Preserve the boundary between framing and verdict.** The standard frames how work should be shaped, classified, and reviewed. It does not score adopter repositories. An implementation that emits a "pass/fail" or "compliance score" derived purely from MCP-side data (without the adopter's own tests and CI) is non-conformant.
4. **Preserve evidence discipline.** When an implementation returns guidance for a defect lane, it must require evidence (failing test, error, repro, anchors) before classifying root cause. Open-ended "what could be wrong?" answers for defect-shaped narratives are non-conformant.
5. **Preserve the lane separation.** An implementation may route between lanes but must not collapse one lane into another (e.g., dressing an assurance request as a single bug ticket, or running an investigator router during a delivery prompt).
6. **Expose, do not hide, this charter.** Any vendor-hosted documentation that describes "AADM" must link to this repository as the source of truth.

---

## 4. What an implementation MAY do

Implementations are free to:

- Add proprietary scoring, search, summarization, or UI conveniences **layered above** standard content.
- Bundle context efficiently (e.g., return only the relevant doctrine slice).
- Add new identifiers in a **clearly namespaced** way (e.g., `VENDOR-AUTH-01`) so adopters can distinguish standard from extension.
- Charge for hosted convenience. Charging is permitted; **gating the standard itself behind a paywall is not** — the markdown in this repository is MIT-licensed and must remain reachable without payment.

## 5. How the standard evolves

Changes to the standard follow a documented process:

1. **Propose** in a pull request against this repository. Substantive changes (new AUTH control, new SEAM, new lane stage, new doctrine slice) require a written rationale and a backwards-compatibility note.
2. **Review** by maintainers and any open community comment window.
3. **Ratify** by merge to `main`. The merged version is the standard; prior versions are accessible by git tag.
4. **Echo.** Implementations have a reasonable window (default: 30 days from a tagged release) to mirror the change. Implementations should declare which standard version they enforce.

Numeric identifiers (`AUTH-NN`, `SEAM-NN`, `TRACE-NN`, `HANDOFF-NN`, `AGENT-NN`, `L`-numbers, `SIGL-NN`) are **append-only**. They are not re-used. A retired control is marked `RETIRED` and kept in the catalog.

Identifier *titles* and *obligation text* may be revised. Adopters who pin to a version should reference the git tag.

## 6. The conformance contract (summary)

A separate document, [`CONFORMANCE.md`](CONFORMANCE.md), enumerates the exact testable claims an implementation must meet to use the AADM name. This charter establishes the principle; the conformance document operationalizes it.

---

## 7. Plain-language summary

- This repository is what AADM **is**.
- The hosted MCP, agent skills, and any other tools are how AADM is **delivered**.
- If a tool says one thing and this repository says another, the repository is right.
- Adopters can fork, extend, and override locally — they just have to say so out loud.
- Anyone — with or without the hosted MCP — can use AADM by reading this repository.
